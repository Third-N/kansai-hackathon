# 道中（仮題）

旅程のリアルタイム再最適化。放置RPGの体裁をとっている。
デモ用の操作パネルは入っていない。実時計で動く。

```bash
npm install
npm run dev     # http://localhost:3000
npm run typecheck
```

## 画面

| ルート | 中身 |
|---|---|
| `/` | ホーム。道中にもどる／出立／合流／前の道中 |
| `/plan?mode=solo\|party` | 行き先えらび |
| `/party/[code]` | 待合。あいことば、参加者、出発 |
| `/trip/[id]` | 道中。ゲージ、双六の道程、割り込み |
| `/trip/[id]/decide/[roundId]` | せーの。伏せる → カウントダウン → 一斉開示 |
| `/trip/[id]/log` | 道中記。終わってから見る |
| `/host/[id]` | ホスト画面。大画面・幹事端末用。全画面で開く |

## 担当の境界

### A（UI・演出）— このリポジトリの現状
- `components/` と `app/` の見た目、`app/globals.css` のトークン
- 触ってよい。ロジックの入出力の形は変えない

### B（Realtime・状態）
- `lib/store.ts` の `TripStore` を Supabase 実装に差し替える。
  UI は `store` しか触らないので、ここだけで済む
- 今は localStorage 実装。`subscribeMembers` は storage イベントで代用しているので、
  Realtime のチャンネル購読に置き換える
- 想定スキーマは `lib/store.ts` 冒頭のコメント参照
- 「せーの」は `openRound` / `castVetoes` / `reveal` / `subscribeRound` として
  ローカル実装済み。同じ約束を Supabase 側で守る
  - `vetoes` は INSERT のみ許可、**SELECT 不可の RLS**。UIで隠すのは伏せたことにならない。
    ローカル実装でも票は `readVetoes` の外に出していない
  - 全員が購読するのは `rounds` の1行だけ。チャンネルは1本で足りる
  - カウントダウンは端末のタイマーではなく `reveal_at`（サーバー時刻）から逆算する。
    画面側は `secondsUntil()` で毎フレーム引き直しているので、実装を変えてもズレない
  - `reveal` は**冪等**。開示済みなら何もせず返し、開示時刻より前でも何もしない。
    `subscribeRound` が時刻超過を見つけたら誰の端末でも呼ぶので、幹事が落ちても止まらない

### C（体力・混雑・再構成）
- `lib/model.ts` の `simulate` と `proposeRevision` が境界。
  戻り値の形（`SimResult` / `Revision`）を保てば中身は全部差し替えてよい
- `K` が係数、`INITIAL_HP` / `INITIAL_MP` が初期値
- `MIN_END_HP` / `MIN_TROUGH_HP` は再構成案に求める余裕。予測が外れる分を残している
- `lib/spots.ts` の `crowdByHour` は時間帯別の推定値。リアルタイムではない。
  ここに天候と自アプリ利用者の位置分布を足す
- `travelMinutes` は表に無い組を直線距離で近似している。経路APIに置き換える

## 設計上、崩してはいけない点

1. **ダメージは事前に出す。** 事後の「−30」は不快を可視化するだけ。
   `Track` が未来の区間の増減を先に描いているのはこのため
2. **落とすときは必ず言う。** `proposeRevision` は行き先を落とす案に重い罰則をかけ、
   並べ替えと短縮で足りるならそちらを選ぶ。落とす場合は文面の先頭で明示する
3. **効果が無いことを効果があるように書かない。** 混雑の改善は、
   元の時刻より実際に下がったときだけ文面に出す
4. **呼び出しは1日5回まで。** `callsUsed` が上限に達したら割り込みを出さない
5. **パーティでは個人を出さない。** ゲージは一番きつい人（`staminaFactor` の最大）に
   合わせて計算し、表示は「パーティに1人、限界が近い人がいます」だけ

## せーのの数値

`vetoCap(選択肢の数)` が1人あたりの上限。上限が無いと全滅が通常ケースになる。
一様ランダムでの実測（4000回）:

| 選択肢 | 人数 | 上限 | 全滅率 |
|---|---|---|---|
| 4 | 5 | 1 | 約25% |
| 4 | 10 | 1 | 約78% |
| 6 | 20 | 2 | 約100% |

**デモの本番は5〜7人でやること。** 会場全員を入れると必ず全滅し、
「反対ゼロ」という売りが毎回「妥協点」に化ける。
全滅時は反対が最少のものを妥協点として出す（`kind: "compromise"`）。設計通りの挙動。

- `/public/icon-192.png` と `/icon-512.png`（manifest が参照している）
